## Architecture

### Backend

- **A run is owned by the server, not by a browser tab.** `RunSessionController` (`POST /run`) writes the run record and spawns `benchmark:run` detached; that command runs every stage of the queue and appends console output to the run's log. Clients poll `GET /run/log?offset=` to follow it, so any number of tabs — in any browser, on any device — see the same run, and any of them can stop it with `POST /run/cancel`. Closing the tab or reloading does not affect the run.
- `App\Support\RunState` is the durable record behind that (`storage/app/benchkit`: `run.json`, `run.log`, `cancel`). It is also what enforces one run at a time: the claim is held by a live PID, checked with signal 0, so an abandoned run reconciles itself to `interrupted` on the next read instead of blocking new runs.
- `App\Support\BenchmarkStages` maps a run's settings to the stages to run and the command each needs, using the builders in `app/Support/` (`YabsCommand`, `CfSpeedTestCommand`, `HttpBenchCommand`, `PhpBenchCommand`). It is the server-side twin of the `enabledBy` map in `useBenchmarkQueue.js` — change them together. `App\Support\BenchmarkProcess` runs one command (Symfony Process wrapped in `script -qe /dev/null -c ...`) and hands each output line to a callback.
- Controllers in `app/Http/Controllers/Benchmarks/` are now read-only: they expose each stage's parsed results at `GET /{stage}/results`. Stages are never started individually.
- Result parsing lives in `app/Actions/Results/` — one class per stage extending the `BenchmarkResults` base (results path + JSON read guard), plus `AssembleResultsDocument` which merges specs and all stage outputs into the unified `/results` document.
- Run snapshots (`app/Actions/Runs/`) freeze a completed run into a JSON document on the `runs` disk (`storage/app/runs`); there is still no database persistence for results. The run process saves its own snapshot via `SaveRunFromState` when the last stage finishes, so a run completes and is recorded even with no browser open; the outcome (`saved`/`empty`/`failed`) is written back onto the run state and a failed save is retryable via `POST /run/save` without re-running anything.
- Environment specs come from `app/Actions/Specs/` (`ServerSpecs`, `PhpSpecs`, `LaravelSpecs`), invoked directly via `(new ClassName)->execute()`. They shell out to `/proc`, `sysctl`, and `artisan about --json`, and are designed to run inside the Linux container.
- Classes in `app/Benchmarks/Php/` are run by **phpbench** (`phpbench.json`, bootstrap `phpbench-bootstrap.php`), NOT PHPUnit. They use `#[Bench\...]` attributes and create/drop their own tables (`benchmark_products`, `benchmark_users`) at runtime — these tables intentionally have no migrations.
- Database migrations are the stock Laravel skeleton only (users/cache/jobs). The dev database is SQLite at `.infrastructure/volume_data/sqlite/database.sqlite`.
- `laravel/mcp` is installed but unused — there is no `app/Mcp` or `routes/ai.php`. Adding MCP features is greenfield. (The `.mcp.json` in the repo belongs to Laravel Boost's own MCP server, unrelated.)

### Frontend

- The home Inertia page, `resources/js/Pages/Index.vue`, toggles `Pages/Partials/{Home,Running}.vue` based on benchmark state; saved runs get their own pages under `Pages/Runs/` (`Index`, `Show`, `Compare`). Layouts are assigned via `defineOptions({ layout: AppLayout })`. It hydrates from the `activeRun` Inertia prop, which is how a freshly loaded page joins a run already in progress.
- Shared state lives in composables using module-scope singleton reactive state: `useBenchmarkQueue` (follows the server's run — it does not drive stages), `useRunSession` (the `/run` endpoints), and `useSettings` (a module-level Inertia `useForm` holding benchmark options). Parametrized composables (`useRunSummary`, `useRunComparison`, `useHostDetails`, …) are pure and hold no module state.
- `useBenchmarkQueue` polls once a second while a run is live and every five seconds while idle, so a tab sitting on the start screen picks up a run started elsewhere rather than offering a button that would be refused.
- Stage metadata (keys and display labels) is centralized in `resources/js/stages.js`; fetch CSRF helpers in `resources/js/http.js`.
