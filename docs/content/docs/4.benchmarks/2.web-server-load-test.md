description: The four routes, the simulated-I/O route, and how the run is warmed and timed.
---

The load test drives four routes with [oha](https://github.com/hatoo/oha), each served **without session/CSRF middleware** so it measures the framework request path rather than session bookkeeping:

- **Static** — a plain string. The framework ceiling; no database.
- **JSON API** — a 25-item JSON payload built in PHP.
- **DB read** — 20 rows from a small table (`SELECT … LIMIT 20`).
- **I/O-bound** — sleeps a configurable delay (default **100 ms**) to model a request whose time is dominated by **one outbound dependency call** (a database over a socket, a cache, an HTTP API).

## Why the I/O-bound route exists

Octane/FrankenPHP **worker mode** wins by skipping Laravel's per-request bootstrap. That is a
roughly fixed amount of work per request, so it is a large share of a static route and a small
share of a request that spends 100 ms waiting on a database. Raising the delay is how you find
out where your own application sits on that scale.

It is a **simulated** delay, labeled as such everywhere. It models the *latency profile* of an
I/O-bound request rather than making a real network call, which would add non-reproducible
variance and an external dependency.

::warning
**This route is also where PHP-FPM's pool size shows up, and the two effects are easy to
confuse.** A blocking sleep holds an FPM worker for its whole duration, so throughput here can
never exceed `pm.max_children ÷ delay`. A pool of 20 workers at 100 ms tops out around 200
requests/sec regardless of hardware. If your connection count is higher than the pool size, you
are measuring the pool.

BenchKit detects the pool size, records it with the run, and flags the load test when this
happens. Check that flag before reading anything into an FPM-versus-worker-mode comparison.
::

## Warmup and duration

Each route is **warmed up** (a short, discarded load pass) before the measured window, so a cold OPcache/JIT, an unprimed route/config cache, and a just-booted worker don't land in the numbers. The default measured window is **30s** (Full preset) or **10s** (Quick preset), overridable per run and always disclosed alongside the result.

::note
Bars in the results scale **within each route** (to its own slowest percentile), so the I/O route's much larger latency doesn't flatten the others into unreadable stubs. The absolute milliseconds sit beside each bar for cross-route comparison.
::
