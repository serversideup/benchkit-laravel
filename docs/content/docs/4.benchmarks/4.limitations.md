---
title: Known limitations
description: Read these before quoting a BenchKit number.
---

None of these are dealbreakers, but together they mean the **absolute** numbers aren't a stand-in for your real application, and cross-host comparisons of light workloads can live inside the noise floor. Being explicit about them is the point.

## The load generator is co-resident (loopback)

By default `oha`, the app, the database, and result-writing all share the same box, so they compete for CPU. This keeps the request path identical across image variations (good for A/B comparison on one machine) but means the **absolute** numbers aren't a clean measure of application capacity.

::tip
To take the generator off-box, use the app's *"Test from your own machine"* panel and run the commands from a **separate machine**.
::

## SQLite by default

The DB-read route and CRUD stage use an in-process SQLite database with a small dataset. That removes connection cost and real data volume/indexing/contention. Point `DB_CONNECTION` at MySQL/Postgres for a production-shaped database — see [Adding a real database](/docs/configuration/adding-databases). The result panel discloses which engine ran.

## A single concurrency point

One connection count is one point on a capacity curve — a server can win at 50 connections and lose at 500. Vary the connection count to map the curve.

## Synthetic routes

Real endpoints have auth, middleware, N+1 queries, cache layers, and outbound calls that these routes don't model. Framework overhead is typically a small fraction of a real request.

## FPM pool tuning matters

Under PHP-FPM a request holds a worker for its entire duration, so `pm.max_children` sets a
hard ceiling on concurrency that no amount of CPU can lift. On the simulated-I/O route this
dominates: 20 workers at 100ms per request cannot exceed about 200 requests/sec.

BenchKit detects the pool size, records it with the run, and **flags the load test when the
connection count exceeds it** — that run measured the pool, not the application. It also
discloses the captured PHP `.ini` tuning in the Environment panel. A fair comparison means
comparing **tuned against tuned**, and saying which tuning you used.

## OPcache off invalidates everything

With OPcache disabled, PHP recompiles your source on every request and throughput drops several
times over. It is the single most impactful setting here, and it is easy to miss on a
misconfigured or outdated image. BenchKit warns before the run and labels the result, but if
you see the warning, fix it and re-run rather than interpreting the numbers.

---

::warning
The takeaway bears repeating: **measure your own real workload.** BenchKit is a comparison and learning tool, not a production profiler.
::
