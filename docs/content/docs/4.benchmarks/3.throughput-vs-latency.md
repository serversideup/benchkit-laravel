---
title: Throughput vs. latency
description: Why the built-in p99 is indicative, and how to measure tail latency honestly.
---

The built-in load test is a **closed-loop saturation test**: it holds a fixed number of connections open and measures maximum throughput. That is the right model for "how much can this box serve?" and for ranking hardware.

A fixed-connection run, however, is subject to **coordinated omission** (Gil Tene): when the server slows, the client simply waits instead of piling on, so the reported **p95/p99 latency is optimistic** — sometimes by an order of magnitude. We're upfront about this. BenchKit:

- labels the built-in run as a saturation/throughput test,
- reports its tail percentiles as **indicative**, and flags any route with fewer than ~1,000 samples as low-confidence, and
- provides a **coordinated-omission-corrected latency command** in the app's *"Test from your own machine"* panel.

## Measuring honest tail latency

The corrected approach uses an **open model** (a fixed request rate) with `--latency-correction`:

```bash [Terminal]
# 1. find max req/s with a saturation run:
oha -z 30s -c 50 https://your-host/bench/db-read

# 2. then measure honest latency at ~70% of that rate:
oha -q <req_per_sec> -z 30s --latency-correction https://your-host/bench/db-read
```

::note
`--latency-correction` is a no-op without a target rate (`-q`), so the second command is required for honest p99s. Run it from a **separate machine** to also avoid the co-resident load-generator effect (see [Limitations](/docs/benchmarks/limitations)).
::

If you care about latency SLOs, use the corrected command. The built-in numbers are for **throughput comparison**.
