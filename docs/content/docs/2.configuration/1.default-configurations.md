BenchKit ships with sensible, production-shaped defaults so results are **comparable across machines** out of the box. You can adjust everything from the settings drawer before a run, and any non-standard value is disclosed alongside the results.

## Presets

Every run starts from a preset:

- **Quick** (a couple of minutes) covers the network, a short web-server load test, and the headline PHP CRUD numbers. Good for a fast read on a box.
- **Full** (around three quarters of an hour) runs everything, including Geekbench and the complete 82-subject PHP suite. Geekbench and the PHP suite are most of that time.
- **Custom** lets you toggle individual stages and tune the load.

The app shows a live estimate as you change settings. Treat it as a rough figure: it is
calibrated on a developer machine, and a small shared vCPU will take longer.

## The standard web-server load

The web-server load test is a **closed-loop throughput (saturation) test**. Every run shares one standard load, which is what makes results comparable:

| Setting | Default | Range |
| --- | --- | --- |
| Duration | `30s` (Full) / `10s` (Quick) | 5–60s |
| Connections | `50` | 1–500 |
| Simulated I/O response | `100ms` | 0–1000ms |

The **simulated I/O response** is the delay the `/bench/io` route sleeps to model one outbound dependency call. Turning it up shows how much of your request time is framework versus waiting, and under PHP-FPM it also runs into the worker pool ceiling. See [the web-server load test](/docs/benchmarks/web-server-load-test).

## OPcache is on by default

The shipped image enables OPcache, and JIT is available, so PHP numbers reflect a real production setup rather than a cold interpreter. Every run's **Environment panel** records the exact `php.ini` tuning behind it: OPcache, JIT, memory, realpath cache, and on FPM the pool size. If OPcache is off, BenchKit warns you before the run and labels the result.

::tip
Want the classic "how much does OPcache matter?" lesson? Run once with it on, once with `PHP_OPCACHE_ENABLE=0`, and compare. See [Customizing the image](/docs/configuration/customizing-the-image).
::

## Where results are stored

Completed runs are saved as JSON snapshots in `storage/app/runs`. Mount a volume there to keep history across restarts (see [Deployment options](/docs/getting-started/deployment-options)).
